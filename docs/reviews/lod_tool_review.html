LOD Tool Review

Every LOD root, both kinds, now sits in one list with an inspector, can be tuned live (thresholds per authored root, a bias, the hysteresis, blending on or off) and shows itself in the viewport: a level view that also marks forced and fallback levels, labels, a ring per threshold, and a white flash when a level pops. Tuning is local to the view and never saved. This review follows the change from a click in the window to a pixel and back to the records.

The change is contained. The tuning is one immutable struct on the scene thread that every pick reads through one function (tunedLodHeuristic), so the GPU pick, the CPU pick for streaming roots, the inspector and the records cannot disagree about thresholds. The GPU gains two push constants and four more bits of state per group; nothing new runs per instance except one extra state read in gbuffer.vert. Open questions: the override key for non-instanceable references, the per-frame state readback at scale, and the gap for streaming roots (no forced/fallback pattern, no pop flash). The change also fixes a validation warning left by the blending commit.

The flow

From a tuning edit to a flashing pixel, and back to the window

The window asks; the scene thread owns the tuning and rebuilds the records; the GPU picks, flags and tags; the lighting pass draws the patterns; the readback feeds the rows, the inspector and the records. Numbers match the walkthrough.

Tinted boxes are new behaviour. Untinted ones changed shape only or are plumbing the change rides on. Dashed arrows are data the main thread reads, not requests.

Walkthrough

Stage by stage

1 · Scene thread

The tuning: one immutable struct, changed only by a request

src/view/viewscene.h · src/view/viewscene.cpp · src/view/placement.cpp (lodRootKey)

Before, the only LOD opinions the view held were hand-set levels, the heuristic toggle and the preference. Now a LodTuning holds a bias, the hysteresis, blending on or off, and threshold overrides by authored root and heuristic index. The window and RPC queue a TuningRequest; applyTuning copies the current tuning, applies the request, refuses what UsdLod couldn't read, and swaps the pointer only if something changed. The snapshot publishes the pointer, so readers on other threads never see a half-applied tuning.

Check here
  • What the key shares. The key is the content the root is authored in plus its path there. Every instance of an instanceable asset shares its prototype's content, so one edit tunes every oak. An oak brought in by a plain reference is composed into the stage: its key is the stage's (-1) and its own path, so it is tuned alone. This is decision 2 as locked, made concrete; whether it matches what an artist expects is the first ask below.
  • The key is stable for the session. Content indices are kept per prototype key in WorldComposer; a released prototype is recomposed at the same index, and indices are never reused for another content. An override therefore survives streaming out and back in. It does not survive opening another scene (open question in the plan).
  • Refusals don't partly apply: a request with bad thresholds changes nothing, including the bias or hysteresis it may carry. Clamping (bias at least 0.01, hysteresis 0 to 0.9) is silent.
  • A tuning change rebuilds every group's record. That is a loop over all groups on the scene thread for each edit, not each frame; at tens of thousands of groups it would be noticeable while dragging the bias slider. Not measured.
2 · Scene thread

One function applies the tuning, for every reader

src/view/viewscene.cpp (tunedLodHeuristic, evaluateLevels) · src/view/placement.cpp (lodGroupOf, LodGroupSource) · src/view/viewcommands.cpp · src/view/lodtool.cpp

tunedLodHeuristic takes an authored heuristic and returns the one the view picks with: the override's lists, the bands dropped when blending is off, then the bias. It is called in five places: the GPU group record (lodGroupOf), the CPU pick for streaming roots (evaluateLevels), the rows' heuristic text, the inspector, and the renderlod record's CPU check. The authored heuristics are never changed.

src/view/viewscene.cppauto tunedLodHeuristic(const LodHeuristic& heuristic, const LodOverride* override, const LodTuning& tuning) -> LodHeuristic {
    auto tuned = heuristic;
    if (override != nullptr) {
        if (override->thresholds) { tuned.thresholds = *override->thresholds; }               // abridged braces
        if (override->blendThresholds) { tuned.blendThresholds = *override->blendThresholds; }
    }
    if (!tuning.blending) {
        tuned.blendThresholds.clear();
    }
    if (tuning.bias != 1.0f) {
        // As if `bias` times closer: a distance's thresholds reached `bias` times farther, a screen size's at a size `bias` squared smaller.
        float scale = heuristic.kind == LodHeuristicKind::Distance ? tuning.bias : 1.0f / (tuning.bias * tuning.bias);
        for (auto& threshold : tuned.thresholds) { threshold *= scale; }
        for (auto& threshold : tuned.blendThresholds) { threshold *= scale; }
    }
    return tuned;
}

Check here
  • Bias on the thresholds, not the measure (a deviation from decision 3's wording, same result). Picking with d against t × bias is the same as picking with d / bias against t; a screen size falls with the square of distance, hence 1 / bias². The GPU needs no new constant, and the measures in the window stay what the camera sees (150 m stays 150 m at bias 2).
  • The hysteresis is not scaled by the bias: it is a fraction, applied to the already-scaled threshold.
  • The inspector needs a render-LOD group's authored heuristics on the main thread; they are published per group slot as LodGroupSource (a shared_ptr per group in SceneDraws), built when the group is placed, not per frame.
  • RenderLodGroup::toWorld/toRoot are now filled for screen-size groups too. The GPU reads them only for distance; the record and the upload bytes for a screen-size group therefore change, which re-uploads such groups once. Baselines are unaffected.
3 · GPU pick

Pops are detected where the level is chosen

shaders/lodselect.comp · src/renderer/passes/lodselectpass.* · src/renderer/rendersnapshot.h · src/renderer/lodgroups.h

The pick is unchanged except that the hysteresis is now a push constant. New: after the drawn level is settled, the shader compares it with last frame's. A change is smooth if a fade led into it (the new level was fading in) or leads out of it (the old level is now the one fading in from the other side). Anything else, a boundary without a band, a forced level, a residency fallback, is a pop: the group's flash countdown is set and the popped counter rises.

Check here
  • A group seen for the first time never pops (previousDrawn is 0xFF when the serial is new), so placing or re-placing a group doesn't flash.
  • The flash is half a second only up to 254 fps. 127 frames is the most 7 bits hold; at 1,000 fps the flash lasts about an eighth of a second. The plan said a fixed frame count; offscreen runs far above 60 fps, so it follows dt instead (deviation).
  • The countdown runs in GPU frames, the length is computed from the main loop's last dt. A hitch makes one flash shorter or longer; it is a visual aid, not a measurement.
  • The forced bit and the countdown are written every frame regardless of whether the tool is open. Cost is a few ALU ops per group, below what the frame timer resolves.
  • The pick rule itself is untouched, so the CPU twin (pickLodLevel) only gained the hysteresis as a parameter; the renderlod check passes it the tuned value.
4 · G-buffer

The level tag carries the group's state to the screen

shaders/lodfade.glsl · shaders/gbuffer.vert · shaders/gbuffer.frag · shaders/gbuffercutout.frag

The normal target's alpha already held the drawn level + 1 for the LOD Level view. lodTag adds three flags from the group's state: 16 forced, 32 falling back (drawn ≠ wanted), 64 flashing. The largest tag is 8 + 16 + 32 + 64 = 120, which a 16-bit float holds exactly. Before, gbuffer.vert wrote the level at location 5 and the fade coverage at location 6; the opaque gbuffer.frag never read location 6, which Vulkan validation reported once per opaque pipeline in every run since the blending commit. Now both travel as one flat uvec2.

shaders/lodfade.glslconst uint lodTagForced = 16u;
const uint lodTagFallback = 32u;
const uint lodTagFlash = 64u;
uint lodTag(uint lodGroup, uint lodLevel) {
    if (lodGroup == 0u || lodLevel == 0u || lodGroup > uint(lodStates.data.length())) {
        return lodLevel;                               // streaming roots and non-LOD meshes: the level only
    }
    uint levels = lodStates.data[lodGroup - 1u].y;
    uint tag = lodLevel;
    if (((levels >> 24) & 1u) != 0u) { tag += lodTagForced; }                 // abridged braces
    if ((levels & 0xFFu) != ((levels >> 8) & 0xFFu)) { tag += lodTagFallback; }
    if ((levels >> 25) != 0u) { tag += lodTagFlash; }
    return tag;
}

  • Every G-buffer vertex now reads the group state once more (it already did for the coverage, same cache line). No new descriptor or binding.
  • Only the G-buffer pipelines carry the tag. Shadow and depth-prepass shaders are untouched.
  • lighting.frag reads tag & 15 as the level, so the flags can't change which colour a level gets. That holds while the level stays below 15; RenderLodGroup::maxLevels is 8.

6 · Readback

Rows, the inspector and the records read the same state

  • The readback cost at scale is unmeasured. 16 bytes a group; the plan's estimate for the old test world was about 740 KB a frame while the tool is shown. On the oak (one group) it doesn't register. The plan's fallback is to read every few frames.

7 · Main thread

The window, the labels and the gizmo

src/ui/lodwindow.* (rewritten) · src/view/lodtool.* (new) · src/debugdraw.* (orientedBox, circle) · src/ui/enginemap.cpp

The window keeps the UI out of the scene: it writes *Requested fields and request lists into LodWindowState, and view.cpp turns them into scene calls once a frame, as the rest of the view's windows do. src/view/lodtool.cpp holds what reads the scene: building and updating rows, the inspection, and the gizmo. src/view/lodtool.cpp · where a screen-size threshold's ring goes// The world distance at which a screen size is reached, for a sphere of `radius` metres in a window of `windowArea` at depth 1.
auto distanceForScreenSize(float radius, float size, float windowArea) -> float {
    if (size <= 0.0f || windowArea <= 0.0f) {
        return 0.0f;
    }
    return radius * std::sqrt(glm::pi<float>() / (size * windowArea));   // inverse of screenSize = π (r/d)² / A
}

  • Rings show the tuned thresholds, so a bias or an override moves them. A screen-size ring depends on the window's field of view and aspect; resizing the window moves it, as it moves the switch.
  • A box's rounded ring is the cut through the box's middle at the threshold distance. Above or below that plane the switch distance is measured to a different part of the box; the ring is exact only in its plane.
  • The label click relies on capturing the mouse for the next frame. A click on the very first frame the cursor enters a label could still reach picking. Not reproducible headless; part of the hand check.

  • The old "set the groups under the selection" control is gone; the "under selection" filter plus "Set shown" does the same for both kinds.

Risks

What to weigh

behaviour

The override key follows USD's instancing, not the asset file (stage 1)

Two oaks referenced from the same file are tuned together only if they are instanceable. Without instancing each is tuned alone, and an artist may expect "the oak" either way.

Keep (it follows where USD keeps the opinion), or key on the referenced asset instead.

cost

Every group's state read back each frame while the tool is shown (stage 6)

An estimate, not measured: about 740 KB a frame on the old test world. A tuning edit also rebuilds every group record on the scene thread.

Accept until the test world measures it, or read the states every few frames now.

scope

Streaming roots get less (stages 4–5)

They show the level colour, labels and the gizmo, but no forced or fallback pattern and no pop flash. Their state is on the CPU; tagging their draws would mean rewriting draw records on each change.

Accept as a named gap, or plan a per-root state buffer for streaming roots.

look

The flash is shorter above 254 fps (stage 3)

7 bits of countdown; at 1,000 fps it lasts about an eighth of a second.

Fine for a debug layer, or count time on the GPU instead of frames.

maintenance

Tuning lives in five readers through one function (stage 2)

Any new reader of thresholds must go through tunedLodHeuristic, or it will disagree with the GPU. The renderlod check catches it for render-LOD groups only.

Acceptable; the README states the rule.
